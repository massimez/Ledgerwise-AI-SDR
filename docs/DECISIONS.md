# Architecture & Implementation Decisions Log (`DECISIONS.md`)

This log tracks every architectural, product, and tooling decision made during the 48-hour build of the **Ledgerwise AI SDR Platform**, including plan adjustments and issues caught during development. It feeds directly into `HOW_I_WORKED.md`.

---

## 2026-11-13 — Phase 0: Repository Audit & Specification Lock

### D1. Keep the `e2e-ai-starter` monorepo foundation
- **Context:** We started with a Bun + Turborepo monorepo (`apps/api`, `apps/web`, `apps/worker`, `packages/db`, `packages/ai-core`, `packages/ui`) providing Better Auth multi-tenancy, Hono RPC, Drizzle ORM (`pgvector/pgvector:pg16`), Mastra AI runtime, and BullMQ workers.
- **Decision:** Keep the infrastructure, authentication, tenant isolation (`withOrg`), and queue plumbing intact; build the SDR domain as first-class modules on top.
- **Why:** Typechecks (`6/6` workspaces) and Ultracite lint (`230` files) pass out of the box. Re-implementing auth, multi-tenancy, or job queues would burn 12+ hours with zero differentiation on the Unscale evaluation criteria.

### D2. Deterministic pipeline with narrow structured LLM steps over an autonomous free-roaming agent
- **Context:** Ledgerwise has five strict rules: (1) never quote a price, (2) never claim anything untrue about a company (every fact from a real source), (3) stop/unsubscribe/not interested → never contact again, (4) answer honestly if asked whether it's a bot, and (5) anything unsure goes to a human.
- **Decision:** Use deterministic code for web fetching, verbatim quote verification against fetched page text, qualification point summation, opt-out regex union, policy routing, and the worker send gate. Use narrow LLM calls with Zod `structuredOutput` for fact extraction, per-criterion evaluation, drafting, fact-check judging, and reply classification/generation.
- **Why:** Hard business rules cannot rely solely on prompt instructions. Enforcing rules in code first, backed by a separate LLM judge and human handoff, guarantees provable compliance and gives every AI action an explicit audit trail (`agent_runs`).

### D3. Outbound email mode: `sandbox` + in-app Prospect Reply Simulator by default, `live` behind env config
- **Decision:** Research real US e-commerce companies, but default to `OUTBOUND_MODE=sandbox` (redirecting outbound emails at the worker send gate to `SANDBOX_RECIPIENT_EMAIL`) and provide an in-app **Simulate Prospect Reply** drawer in `/dashboard/inbox` that enqueues into the real `sdr-inbound` BullMQ pipeline and live-polls the thread until completion.
- **Why:** Prevents sending unsolicited cold emails to real founders during a hiring evaluation while exercising the exact same BullMQ, Mastra, and Cal.com code paths and letting Unscale reviewers test any reply scenario in seconds.

### D4. Qualification scoring adjustment for private $1M–$10M e-commerce brands
- **Initial plan:** Score `unknown` revenue band and `unknown` employee band at `5 / 15` points each.
- **Adjustment (locked):** When a company passes the `us_based` and `ecommerce_brand` gates and has no large-company disqualifier (e.g., >$20M funding, >50 employees, public company, or full CFO+Controller team), award **`10 / 15`** points for `unknown` revenue and **`10 / 15`** for `unknown` headcount (labeled `"Est. fit (unreported)"`).
- **Why:** Private $1M–$10M DTC brands rarely disclose revenue publicly. Giving `5/15` capped base fit at 30 points, which meant a company with a verified timing signal (+20 or +25) would still land in Tier B/C (50–55) instead of Tier A (≥70). At `10/15`, base fit with a contact is 40 points, so 1–2 verified timing signals naturally place strong leads into Tier B (60–65) or Tier A (70+).

### D5. Conversational first emails (<100 words, no physical address footer)
- **Initial plan:** ≤120 words with a physical mailing address footer.
- **Adjustment (locked):** Keep first emails under **100 words**, conversational, plain text, with zero links, zero pricing, one sourced observation, one Ledgerwise value line, and a soft call CTA — without a physical address footer.
- **Why:** Shorter, human-sounding cold emails read like a founder-to-founder note rather than a marketing blast.

### D6. AI disclosure default: `when_asked`
- **Decision:** Default `sdr_settings.ai_disclosure` to `when_asked` (while still supporting `always` as a workspace setting). When the reply classifier detects `asksIfBot = true`, the reply generator answers honestly that it is Ledgerwise's AI SDR assistant working with the sales team, and a deterministic output guard verifies the disclosure phrase is present before sending.
- **Why:** Matches Ledgerwise's explicit rule ("If someone asks whether they're talking to a bot, answer honestly") without adding robotic boilerplate to every outbound message.

### D7. LLM Provider: OpenRouter + VPS Docker Compose hosting
- **Decision:** Use OpenRouter (`OPENROUTER_API_KEY`) via Mastra's `openrouter/...` model router, and deploy the full stack (`web`, `api`, `worker`, `postgres`, `redis`, `caddy`) via Docker Compose on a dedicated VPS.
- **Why:** OpenRouter gives single-key access to fast and high-reasoning models with built-in spend tracking, and Docker Compose on a VPS avoids multi-vendor free-tier sleep/connection limits over the 2-week evaluation window.

### D8. Phase 0 bugs caught and fixed in M0 (F1–F3)
- **F1 (Boot/test blocker):** Root `.env` has empty strings (`GOOGLE_GENERATIVE_AI_API_KEY=""`, `OPENAI_API_KEY=""`, `ANTHROPIC_API_KEY=""`, `OPENROUTER_API_KEY=""`), which caused `z.string().trim().min(1).optional()` in `apps/api/src/env.ts` to throw `Invalid API environment variables` on import, failing 9 test suites. Fixed by normalizing empty/whitespace strings to `undefined` before validation.
- **F2 (Prod S3 requirement):** Removed `S3_ACCESS_KEY_ID` and `S3_SECRET_ACCESS_KEY` from `requiredInProd` in `apps/api/src/env.ts` (enforcing only that if one is set, both are set), since the SDR platform does not require S3 object storage.
- **F3 (Public sign-up lock):** Added `DISABLE_SIGNUP` boolean env variable wired to Better Auth's `emailAndPassword.disableSignUp` and `emailOTP.disableSignUp`.

## 2026-11-14 — Mastra Agent Orchestration & Studio Integration

### D9. Narrow Mastra agents orchestrated by plain TypeScript pipelines instead of Mastra `createWorkflow`
- **Context:** The initial design spec (`docs/specs/2026-11-13-ledgerwise-sdr-design.md`) called for adding SDR agents and Mastra workflows to `packages/ai-core`. In practice, SDR execution runs across `apps/worker` (BullMQ `sdr-pipeline-queue`, `sdr-outbound-queue`, `sdr-inbound-queue`) and `apps/api` with PostgreSQL domain tables (`companies`, `threads`, `messages`, `agent_runs`) owning lifecycle state.
- **Decision:** Keep the 5 narrow Mastra `Agent` definitions (`researchExtractorAgent`, `firstEmailWriterAgent`, `factCheckJudgeAgent`, `replyClassifierAgent`, `replyGeneratorAgent` in `packages/ai-core/src/sdr/agents/factory.ts`) with Zod `structuredOutput` schemas, and orchestrate them through plain TypeScript pipeline functions (`runCompanyResearchPipeline`, `generateVerifiedFirstEmail`, `runInboundReplyPipeline`) rather than Mastra `createWorkflow` definitions. Register the 5 SDR agents in Mastra Studio via a Studio-only `includeSdrAgents: true` flag on `createMastraRuntime()` in `packages/ai-core/src/mastra/index.ts` (keeping `includeSdrAgents` disabled in `apps/api/src/modules/ai/service.ts` so `/dashboard/ai` continues exposing only `workspace-assistant`).
- **Why:**
  1. **Avoid dual state machines:** BullMQ + PostgreSQL domain tables already manage retries, queues, thread/message states (`pending_review`, `needs_human`, `opted_out`), and `agent_runs` telemetry. Adding Mastra's workflow execution/suspension engine would introduce a second, competing state machine to keep synchronized.
  2. **Deterministic guardrails and unit testability:** Plain TypeScript pipelines keep deterministic steps—verbatim quote verification, scoring, opt-out regex union, pricing/link/word-count guards, bot disclosure checks, and `< 0.75` confidence escalation—explicit in code and directly unit-testable with `bun test` without a Mastra workflow runtime or database harness.
  3. **Targeted Studio observability:** A Studio-only `includeSdrAgents` flag gives visual prompt/model inspection for all 5 SDR agents in Mastra Studio (`bun run mastra:studio` on port `4111`) without exposing internal extractor, judge, or classifier agents to end users in `/dashboard/ai`.

### D10. Remove client-side SDR mock and fallback data in `apps/web`
- **Context:** `apps/web/src/lib/sdr-fallback-data.ts` and `apps/web/src/lib/sdr-hooks.ts` contained in-memory fallback datasets (`INITIAL_FALLBACK_*`, `mem*` arrays), `buildFallbackSummary()`, and client-side simulated inbound processing (`processFallbackSimulatedInbound()`), silently masking API/database errors with mocked data.
- **Decision:** Deleted `apps/web/src/lib/sdr-fallback-data.ts`, extracted pure TypeScript domain/summary interfaces into `apps/web/src/lib/sdr-types.ts`, removed all fallback data and `catch` fallbacks from `apps/web/src/lib/sdr-hooks.ts`, updated `apps/web/test/playbook-types.test.ts` to use a local test fixture, and added explicit error/retry states across the SDR dashboard views (`sdr-today-client.tsx`, `companies/page.tsx`, `review/page.tsx`, `inbox/page.tsx`, `meetings/page.tsx`, `settings/playbook/page.tsx`).
- **Why:** Ensures the web UI always reflects real backend state from `apps/api` and surfaces genuine request errors instead of silently rendering stale or fabricated demo records.

### D11. Disable curated prospect backfill when `EXA_API_KEY` is set
- **Context:** `discoverProspectCandidates()` in `packages/ai-core/src/sdr/integrations/exa-client.ts` previously backfilled remaining slots up to `targetCount` from `CURATED_US_ECOMMERCE_PROSPECTS` whenever live Exa search returned fewer candidates, and `gatherCompanyResearchDocuments()` in `packages/ai-core/src/sdr/integrations/source-gatherer.ts` could fall back to curated `seedDocuments`.
- **Decision:** When `exaApiKey` is set, `discoverProspectCandidates()` now returns only Exa-discovered candidates without backfilling from `CURATED_US_ECOMMERCE_PROSPECTS`, and `gatherCompanyResearchDocuments()` skips curated `seedDocuments` fallback.
- **Why:** Prevents fixture/sandbox companies or documents from contaminating real Exa discovery batches and evaluation counts.

### D12. OpenRouter -> Google Gemini fallback and explicit failure (`SdrLlmFallbackError`)
- **Context:** SDR pipeline agents in `packages/ai-core` previously checked only `OPENROUTER_API_KEY` and silently fell back to deterministic regex/template output whenever the key was missing or the LLM request failed, without falling back to `GOOGLE_GENERATIVE_AI_API_KEY` or surfacing failures.
- **Decision:** Added shared provider resolution and sequential execution (`resolveSdrModelConfig`, `runSdrAgentWithFallback`, `SdrLlmFallbackError`) in `packages/ai-core/src/sdr/agents/factory.ts`: runs OpenRouter (`SDR_MODEL_FAST` / `SDR_MODEL_SMART`) first when configured, automatically falls back to direct Gemini (`SDR_GEMINI_MODEL` or `MASTRA_DEFAULT_MODEL` `google/*` or `DEFAULT_SDR_MODEL_GEMINI` `google/gemini-3.5-flash`) when OpenRouter key is missing or fails, and throws `SdrLlmFallbackError` across research extraction, first-email drafting/judging, reply classification, and reply drafting when all configured providers fail (or when `requireLlm: true` with no provider keys configured). Wired `GOOGLE_GENERATIVE_AI_API_KEY`, `GOOGLE_API_KEY`, `SDR_GEMINI_MODEL`, and `requireLlm: true` in `apps/worker` and `apps/api` fallback handlers, and updated `handleResearchCompany` to mark the `researchRuns` record as `"failed"` before rethrowing.
- **Why:** Ensures transient OpenRouter failures or missing OpenRouter keys seamlessly use Gemini instead of silently sending template copy, while total provider outages fail loudly instead of masquerading as valid AI output.

### D13. BullMQ custom `jobId` format, thread-history context for confirmation follow-ups, and Inbox live state sync
- **Context:** User testing `/dashboard/inbox` hit two issues: (1) simulated inbound replies fell back to unguarded in-process timers or stayed stuck in `AI working` because `apps/api/src/modules/sdr/queue.ts` passed colons (`outbound:${id}`, `inbound:${id}`) in BullMQ v6 custom `jobId` values, which BullMQ rejects, and unhandled errors failed to clear `threads.pendingJobId`; (2) follow-up messages like `"is it confirmed ?"` lacked prior conversation turns (`recentMessages`) and booking status in `replyClassifierAgent` / `replyGeneratorAgent`, causing silent `needsInfoFromHuman=true` escalation even when the prospect had already picked `"Mon, Nov 16, 10:00 AM"`, while `useSdrThreads` did not invalidate when `useSdrThreadDetail` finished polling and `ThreadStatusBanners` scrolled out of view.
- **Decision:**
  1. Replaced colons with hyphens (`outbound-${id}`, `inbound-${id}`) in `apps/api/src/modules/sdr/queue.ts`, added failure/timeout recovery in `apps/api/src/modules/sdr/threads/threads.service.ts` (`STALE_PENDING_THREAD_JOB_MS`, `runOfflineInboundSafely`) and `apps/worker/src/processors/sdr/inbound/inbound.processor.ts` (`recoverTerminalInboundFailure`), and tightened weekday/month-day slot disambiguation in `packages/ai-core/src/sdr/reply/classifier.ts` (`slotMatchesLabel`).
  2. Added `recentMessages` (`InboundThreadMessageContext`) and booking status context across `loadInboundJobRecords`, `executeOfflineInboundFallback`, `classifyDeterministicReply`, `classifyWithOptionalLlm`, and `draftWithOptionalLlm`, plus `BOOKING_STATUS_CHECK_REGEX` + `findPendingSlotFromRecentMessages` so confirmation follow-ups either confirm existing bookings, recover an unaddressed prior slot pick, or answer honestly with offered slots instead of escalating silently.
  3. Updated `useSdrThreads` (polls while any thread has `pendingJobId`) and `useSdrThreadDetail` (invalidates `["sdr", "threads"]`, `["sdr", "dashboard"]`, `["sdr", "meetings"]`, `["sdr", "companies"]` when `pendingJobId` clears) in `apps/web/src/lib/sdr-hooks.ts`, and pinned `ThreadStatusBanners` above the message scroller in `apps/web/src/app/dashboard/inbox/page.tsx`.
- **Why:** Eliminates silent BullMQ enqueue failures, prevents stale `AI working` badges and hidden escalation banners in Inbox, and ensures multi-turn booking follow-ups behave deterministically and contextually.

### D14. Contact/privacy probing, verified on-site email extraction, draft gating without email, and Exa + research pipeline logging
- **Context:** Inspecting qualified lead `Lilyandfox` (`lilyandfox.com`, Tier B `65/100`) revealed 0 contacts (`contactId: null`) despite Exa returning `help@lilyandfox.com` on `/pages/privacy-policy` and at character offset `3860` on `/pages/careers-fulfilment-associate`. Four gaps caused this: `probeCompanyWebPresence` did not probe `/pages/contact`, `/pages/contact-us`, `/contact`, `/pages/privacy-policy`, or `/policies/privacy-policy`; `extractWithOptionalLlm` sliced docs to `.slice(0, 5)` and `.slice(0, 2600)`; `researchExtractorAgent` lacked contact-extraction instructions; and `handleResearchCompany` drafted a `pending_review` email even when `primaryContact?.email` was missing, while `searchExaSources` and the research/qualification stages emitted minimal diagnostic logs.
- **Decision:**
  1. Added `SdrPipelineLogger` (`packages/ai-core/src/sdr/research/types.ts`) and wired `workerSdrPipelineLogger` (`apps/worker/src/processors/sdr/pipeline/pipeline-logger.ts`) through `handleDiscoverBatch`, `discoverProspectCandidates`, `searchExaSources` (logging redacted `x-api-key` requests, HTTP status, latency, and result previews), `gatherCompanyResearchDocuments`, `runCompanyResearchPipeline`, and `handleResearchCompany`.
  2. Expanded `probeCompanyWebPresence` (`packages/ai-core/src/sdr/integrations/source-gatherer.ts`) to include contact and privacy pages; updated `researchExtractorAgent` instructions (`packages/ai-core/src/sdr/agents/factory.ts`); added `selectPromptDocuments` (up to `8` docs, `4000` chars) and `resolveVerifiedContact` (`packages/ai-core/src/sdr/research/company-pipeline.ts`) backed by `extractVerifiedDomainEmailsFromDocs`, `verifyEmailInDocs`, `pickBestDomainContactEmail`, and `isGenericMailboxEmail` (`packages/ai-core/src/sdr/research/fact-extractor.ts`).
  3. Updated `handleResearchCompany` (`apps/worker/src/processors/sdr/pipeline/research-company.handler.ts`) so `shouldDraft` requires `Boolean(primaryContact?.email?.trim())` — qualified companies with zero verified contact emails log a warning instead of creating unsendable `contactId: null` drafts.
- **Why:** Ensures real on-site domain emails are extracted and verified against fetched text (without synthetic fallback addresses), blocks unsendable drafts when no contact email exists, and provides full redacted Exa + research/qualification traceability in worker logs.

### D15. Discovery pipeline separation of signal evidence URLs from resolved company domains
- **Context:** Exa `hiring_finance_ops` searches returned valid job listings hosted on third-party ATS/job-board domains (`greenhouse.io`, `workable.com`, `breezy.hr`, `wellfound.com`, `builtin.com`) or deep `/careers` URLs, which were skipped or collapsed onto ATS hosts by `toCandidateFromExaDoc` instead of resolving each employer's official website domain.

Updated `searchExaSources` and `discoverProspectCandidates` (`packages/ai-core/src/sdr/integrations/exa-client.ts`): when `companyDomain` is absent from the snippet and the result URL is a third-party signal host (`isThirdPartySignalHost`), resolves the official domain via a cached Exa `category: "company"` search (`lookupCompanyDomainViaExa`), runs `existingDomains` deduplication against `resolvedDomain`, and returns `evidenceUrl` + `evidenceQuote` alongside `seedDocuments`.

Updated `discover-batch.handler.ts`, `pipeline.repository.ts`, and `research-company.handler.ts` to pass LLM credentials to discovery, persist discovery `evidenceUrl`/`evidenceQuote` into `evidence` at company creation (`insertDiscoveredCompanyWithContact`), and feed existing verified discovery evidence into `runCompanyResearchPipeline` without duplicating rows.
- **Why:** Prevents losing valid ATS/job-board/deep-path discovery leads and ensures third-party hiring evidence persists directly onto the company record for qualification and drafting.

### D16. Dynamic `startPublishedDate` recency cutoffs for Exa discovery presets
- **Context:** Exa searches for `recent_funding` returned outdated 2015–2019 funding articles because `startPublishedDate` was omitted from the `/search` request body.
- **Decision:** Added `resolveDiscoveryStartPublishedDate` (`packages/ai-core/src/sdr/integrations/exa-client.ts`, exported via `packages/ai-core/src/sdr/integrations/research.ts`) mapping time-sensitive presets to rolling ISO 8601 lookback windows (`hiring_finance_ops`: `180` days, `recent_funding`: `270` days, `channel_expansion`: `365` days), wired `startPublishedDate` into `searchExaSources` and `discoverProspectCandidates` (and logged it in `ExaSearch` / `SdrDiscovery`), while leaving `company_domain_lookup` and `company_research` undated so evergreen company websites remain searchable.
- **Why:** Prevents multi-year-old funding/expansion news or closed job posts from entering active prospecting pipelines.

### D17. BullMQ rate limiting (10 jobs/min) and pre-LLM source document persistence
- **Context:** Running `gemini-3.5-flash-lite` under the 15 RPM free-tier limit with concurrent BullMQ workers triggered HTTP 429 bursts, and BullMQ retries re-executed `SdrSourceGatherer` (`gatherCompanyResearchDocuments`), burning duplicate Exa API requests and web scrapes.
- **Decision:**
  1. Added `SDR_LLM_RATE_LIMITER` (`max: 10, duration: 60_000`, marked `TODO: Increase later`), `buildSdrPipelineWorkerOptions`, and `buildSdrInboundWorkerOptions` (`concurrency: Math.min(2, workerConcurrency)`) in `apps/worker/src/lib/sdr-queues.ts`, wired into `sdrPipelineWorker` and `sdrInboundWorker` in `apps/worker/src/index.ts`, with 15s exponential backoff on `pipelineQueue` (`PIPELINE_SDR_JOB_OPTIONS`) and `enqueueSdrPipelineJob` (`apps/api/src/modules/sdr/queue.ts`).
  2. Added the `company_source_docs` Drizzle table (`packages/db/src/schema/sdr.ts`, `packages/db/src/schema/relations.ts`, and `packages/db/migrations/0005_nebulous_sunspot.sql`) plus `deduplicateSourceDocuments`, `loadCachedCompanySourceDocs` (24h TTL `SOURCE_DOC_CACHE_TTL_MS`), and `persistCompanySourceDocs` in `apps/worker/src/processors/sdr/pipeline/pipeline.repository.ts`.
  3. Updated `handleResearchCompany` (`apps/worker/src/processors/sdr/pipeline/research-company.handler.ts`) via `loadOrGatherCompanySourceDocs` to persist gathered documents to `company_source_docs` before calling `runCompanyResearchPipeline` and reuse fresh cached documents on retries without re-calling `gatherCompanyResearchDocuments`.
- **Why:** Smooths LLM bursts below Gemini's 15 RPM free-tier ceiling and prevents BullMQ retries from re-running Exa/web/ATS gathering.

## 2026-11-14 — Domain Resolution Matching, Exa Lookup Validation, and Strict 5–50 Employee Bounds

### D20. Company-to-hostname `first_party_url` matching, `exa_company_lookup` result validation, and strict 5–50 employee bounds
- **Context:** Latest discovery/research logs surfaced three precision bugs: (1) `STELLE ATHLETICA INC` and `Petite Plume` resolved with `resolutionSource: "first_party_url"` onto unlisted job-board domains (`zunohire.com`, `meterwork.com`), causing invalid pattern-derived emails; (2) `lookupCompanyDomainViaExa` for `Kontoor Brands` skipped LinkedIn (`results[0]`) and accepted `results[1]` (`kmdbrands.com`, a different company) without checking that title/text/hostname matched the target company; (3) `Petite Plume` explicitly stated `"71 Employees"` in source text, yet LLM extraction returned `employeesInRange: "yes"` and awarded `15/15` points instead of disqualifying outside `5–50`.
- **Fix:**
  1. Added `zunohire.com`, `meterwork.com`, `jobsearcher.com`, `opentoworkremote.com`, and `career.io` to `EXA_DISCOVERY_EXCLUDED_JOB_BOARD_HOSTS` (plus `discoveryExtractorAgent` instructions/schema) and added company directory hosts (`zoominfo.com`, `dnb.com`, `apollo.io`, `rocketreach.co`, `craft.co`, `owler.com`, `cbinsights.com`, `tracxn.com`, `yelp.com`, `bbb.org`, `manta.com`, `comparably.com`, `ambitionbox.com`, `builtwith.com`, `similarweb.com`, `sec.gov`, `finance.yahoo.com`, `pinterest.com`) to `THIRD_PARTY_SIGNAL_HOSTS` in `packages/ai-core/src/sdr/integrations/exa-client.ts`.
